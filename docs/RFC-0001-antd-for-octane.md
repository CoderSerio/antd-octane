# RFC-0001：在 Octane 中实现 Ant Design 组件库

- 状态：草案，征求意见
- 日期：2026-09-24
- 暂定包名：`antd-octane`

## 1. 为什么做

希望熟悉 Ant Design 的开发者在使用 Octane 时，仍能沿用熟悉的组件、交互方式和主题配置，减少重新选择组件库和学习 API 的成本。

计划使用 Octane 实现组件，参考 Ant Design 的 API 和设计体系。是否值得独立维护一套实现，需要通过原型验证适配成本和实际使用体验；目前不宣称性能优势。

## 2. 兼容到什么程度

首版拟以 Ant Design v5 为参考，开始实现前锁定具体版本。选择 v5 还是直接跟进 v6，也是本次 RFC 希望确认的问题。

| 方面 | 拟采用的原则 |
| --- | --- |
| 组件 API | 尽量保持组件名、常用属性、事件参数和组合方式一致 |
| 交互与视觉 | 对照上游示例验证状态、键盘操作、焦点、主题和布局 |
| 框架行为 | 以所选 Octane 版本为准，逐项验证事件、ref、context 和渲染行为 |
| 兼容差异 | 按组件公开支持范围、差异和迁移说明 |

不承诺仅替换 import 即可运行，也不预先承诺全部组件、内部 DOM 或 React 运行时行为完全一致。ProComponents、移动端组件和自动迁移工具不在首版范围内。

## 3. 先解决哪几个问题

### 组件 API 如何适配 Octane？

[Octane 当前文档](https://github.com/octanejs/octane#readme)采用接近 React 的编程模型，不能直接套用其他响应式框架的 API 假设。先用小例子验证以下边界，再确定组件约定：

- **输入与受控状态**：`value`、`defaultValue`、`checked` 和 `onChange` 如何配合；输入法组合输入时是否正常。
- **ref 和渲染回调**：如何暴露 `focus()` 等方法；`Table.columns.render` 中的状态更新是否正确。
- **context 与浮层**：主题、语言如何传入弹窗；`Modal.confirm` 等命令式调用如何创建和销毁实例。

### 样式和底层能力能复用多少？

希望沿用 Ant Design 的 token 体系和主题配置，但不预设 `@ant-design/cssinjs` 能直接在 Octane 中使用。先用 `Button + ConfigProvider` 验证样式生成、主题切换和样式清理，再决定直接复用、适配或移植。

图标数据、工具函数等优先评估框架无关的实现。浮层定位、键盘操作、焦点管理和表单状态统一处理，避免每个组件各写一套。复用与移植范围以依赖检查和可运行示例为依据。

### 首版做多大，怎样算完成？

先完成一组能实际使用的小范围组件，不以组件数量作为首版目标：

1. **主题与基础组件**：`ConfigProvider`、`Button`，验证 token 和主题切换。
2. **输入与状态**：`Input`、`Checkbox`，验证受控状态、事件和 ref。
3. **浮层与组合**：`Modal`，验证挂载、关闭、焦点恢复和 context。

这些验证通过后，再推进基础 `Form`、`Table`，组成“列表 → 弹窗编辑 → 提交”的示例。具体 alpha 范围根据结果确定。

首个 alpha 应能在独立 Octane 项目中安装运行，包含使用示例、关键交互测试和已知差异清单。SSR 支持单独验证并标明状态，不以浏览器端通过代替。

## 4. 后续如何维护

组件先放在一个主包中，共享主题和基础能力。记录所参考的 Ant Design、Octane 版本，以及每次移植对应的上游提交和测试；升级时按组件检查变化。

涉及 API 差异的决定在验证后补充到文档。未实现的能力明确标注，不用占位组件表示已经支持。

## 5. 希望获得的反馈

- 首版参考 v5，还是直接以 v6 为基线？
- 哪些 API 和交互必须保持一致，哪些差异可以接受？
- 样式、浮层和表单等底层能力，有哪些适合复用的实现或需要提前验证的限制？
- 上述原型范围是否足以判断方案可行，是否遗漏关键场景？

本 RFC 用于讨论方向和技术边界。原型结果出来后，再收敛 API 约定、首版范围和发布计划。
