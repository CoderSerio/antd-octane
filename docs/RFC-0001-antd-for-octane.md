# RFC-0001：在 Octane 中实现 Ant Design 组件库

- 状态：初步方案，征求意见
- 日期：2026-09-24
- 暂定包名：`antd-octane`

## 1. 为什么做

希望熟悉 Ant Design 的开发者在使用 Octane 时，仍能沿用熟悉的组件、交互方式和主题配置，减少重新选择组件库和学习 API 的成本。

计划使用 Octane 实现组件，参考 Ant Design 的 API 和设计体系。是否值得独立维护一套实现，需要通过原型验证适配成本和实际使用体验；目前不宣称性能优势。

## 2. 已有的初步结论

以下是前期讨论形成的方案，作为实现和评审的起点；它们不代表已经实现或通过兼容性验证。

- **版本基线**：0.x 先对齐 Ant Design v5，开始实现前锁定具体版本。后续再跟进 v6，不同时承诺两套完整实现。
- **实现方式**：使用 Octane 实现组件，不包装 React 版 antd；底层能力在验证后可复用已有 Octane 实现。
- **API 边界**：高频业务 API 优先保持 antd 用法；状态、生命周期和 ref 接入方式遵循 Octane。主题、语言等一次性配置允许有必要的差异，但必须说明。
- **主题与图标**：沿用 antd 的 seed/map/alias token 体系，优先复用样式能力和 `@ant-design/icons-svg` 图标数据，不另起一套设计体系。
- **包结构**：采用一个主组件包 `antd-octane`，共享基础能力，不为每个组件单独发布 npm 包。
- **覆盖方向**：逐步覆盖 antd 核心组件。先验证主题和基础交互，再扩展 Form、Table 等复杂组件；完整覆盖是后续目标，不作为首个 alpha 的发布承诺。

具体到常用 API，已有以下意向：

| API | 初步结论 | 仍需验证 |
| --- | --- | --- |
| 输入组件 | 保留逐次输入触发 `onChange` 的常用行为及 `value` / `checked` 受控用法 | Octane 事件适配、输入法和状态同步 |
| `Form` | 保留 `rules` 数组结构和常用校验配置 | 动态规则、异步校验与字段依赖 |
| 命令式反馈 | 保留 `Modal.confirm`、`message`、`notification`，同时提供能获取上下文的调用方式 | context 传递、实例销毁，以及 `Modal.useModal` 等接口的适配 |
| `ConfigProvider` | `theme` 接收配置对象，支持主题切换 | token 计算、样式更新与清理 |
| 组件 ref | 按组件保留 `focus()`、`blur()` 等方法和必要的 DOM 访问能力 | 以 Octane 实际 ref 机制确定接入写法 |

状态传值和 ref 的具体写法，以锁定版本的 Octane 文档和验证结果为准。

### 兼容边界

| 方面 | 拟采用的原则 |
| --- | --- |
| 组件 API | 尽量保持组件名、常用属性、事件参数和组合方式一致 |
| 交互与视觉 | 对照上游示例验证状态、键盘操作、焦点、主题和布局 |
| 框架行为 | 以所选 Octane 版本为准，逐项验证事件、ref、context 和渲染行为 |
| 兼容差异 | 按组件公开支持范围、差异和迁移说明 |

不承诺仅替换 import 即可运行，也不预先承诺全部组件、内部 DOM 或 React 运行时行为完全一致。ProComponents、移动端组件和自动迁移工具不在首版范围内。

## 3. 先解决哪几个问题

### 组件 API 如何适配 Octane？

[Octane 当前文档](https://github.com/octanejs/octane#readme)采用接近 React 的编程模型，不能直接套用其他响应式框架的 API 假设。在上述初步方案下，用小例子验证以下边界，再确定具体实现约定：

- **输入与受控状态**：`value`、`defaultValue`、`checked` 和 `onChange` 如何配合；输入法组合输入时是否正常。
- **ref 和渲染回调**：如何暴露 `focus()` 等方法；`Table.columns.render` 中的状态更新是否正确。
- **context 与浮层**：主题、语言如何传入弹窗；`Modal.confirm` 等命令式调用如何创建和销毁实例。

### 样式和底层能力能复用多少？

希望沿用 Ant Design 的 token 体系和主题配置，但不预设 `@ant-design/cssinjs` 能直接在 Octane 中使用。先用 `Button + ConfigProvider` 验证样式生成、主题切换和样式清理，再决定直接复用、适配或移植。

图标数据、工具函数等优先评估框架无关的实现。浮层定位、键盘操作、焦点管理和表单状态统一处理，避免每个组件各写一套。复用与移植范围以依赖检查和可运行示例为依据。

### 首版做多大，怎样算完成？

先完成一组能实际使用的小范围组件，不以组件数量作为首版目标：

1. **主题与基础组件**：`ConfigProvider`、`Button`，验证 token 和主题切换。
2. **输入与状态**：`Input`、`Checkbox`，验证受控状态、事件和 ref。
3. **浮层与组合**：`Modal`，验证挂载、关闭、焦点恢复和 context。

这些验证通过后，再推进基础 `Form`、`Table`，组成“列表 → 弹窗编辑 → 提交”的示例。具体 alpha 范围根据结果确定。

首个 alpha 应能在独立 Octane 项目中安装运行，包含使用示例、关键交互测试和已知差异清单。SSR 支持单独验证并标明状态，不以浏览器端通过代替。

## 4. 后续如何维护

组件先放在一个主包中，共享主题和基础能力。记录所参考的 Ant Design、Octane 版本，以及每次移植对应的上游提交和测试；升级时按组件检查变化。

涉及 API 差异的决定在验证后补充到文档。未实现的能力明确标注，不用占位组件表示已经支持。

## 5. 希望获得的反馈

- 以 v5 为首版基线的方案，是否存在需要提前考虑的维护或迁移问题？
- 上述 API 初步结论是否遗漏重要场景？哪些差异会影响实际迁移？
- 样式、浮层和表单等底层能力，有哪些适合复用的实现或需要提前验证的限制？
- 上述原型范围是否足以判断方案可行，是否遗漏关键场景？

本 RFC 用于讨论方向和技术边界。原型结果出来后，再收敛 API 约定、首版范围和发布计划。

## 6. 首版工程与文档站（2026-09-25 补充）

第一阶段交付工程骨架、最小文档站、主题兼容验证和 Button。固定 Octane 0.4.3 与 Ant Design 5.29.3 为验证基线。

- `packages/antd-octane`：单一主组件包，先实现 ConfigProvider、主题和 Button。
- `site`：使用 Octane + Vite，提供中文指南、可运行示例、示例源码、API、主题切换及已知差异。构建为静态站点，部署方式独立配置。
- `playground`：用于调试和问题复现，按需建立；不替代文档站。文档 demo 同时供交互测试使用，不重复维护示例。
- `docs`：保留 RFC 和设计决策。暂不实现在线代码编辑器。

参考 Antdv Next 对正式文档站与开发 playground 的区分，不直接复制其 Vue 文档运行时。

## 7. 主题迁移与样式工具

**主题兼容是验收标准。** 支持范围内的 antd v5 `theme.token`、`theme.components.Button` 配置保持结构和值不变。内置算法导入改为来自本库，并支持默认、暗色、紧凑和算法组合。自定义算法、动态切换、嵌套继承与 `inherit: false` 需要验证。

首版复用固定上游版本的纯 token 算法，保留 MIT 许可和来源记录；组件由 Octane 原生实现。Button 使用静态 CSS 与组件级 CSS 变量消费派生 token，暂不移植整套 CSS-in-JS 引擎。验证使用同一份配置对比原版 antd 的全局 token，并检查组件样式和交互。主题计算兼容不等于全部组件样式兼容。

首版不承诺 `cssVar`、`hashed`、`prefixCls`、StyleProvider 或 SSR 样式契约；原有 Less、深层 DOM 选择器和 React 主题插件需要单独适配。缺失的 Button token 应在支持清单中说明，不能静默宣传为全量兼容。

组件库不要求用户使用 Tailwind CSS 或 StyleX。保留 `className`、`style`，CSS 放入命名 layer，验证 reset、覆盖顺序和主题作用域。Tailwind 与 StyleX 是业务样式工具，也可以用于文档站；是否用作组件库内部引擎是独立决策。首版不把任一工具设为必需依赖，后续补充两者的真实构建消费测试，再声明兼容。

允许评估已有 Octane Base UI 等底层实现；是否复用取决于 antd 行为与主题能否正确映射，不预先排除，也不以包装完成作为兼容证据。
